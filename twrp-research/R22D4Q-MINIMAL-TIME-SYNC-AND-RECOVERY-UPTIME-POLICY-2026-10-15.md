# R22d4q — Minimal Time Sync priority, shared success flag and honest session uptime
> **LATEST APPROVED SOURCE-OF-TIME POLICY (2026-10-15):** Time Sync is the **ONLY authority** for recovery calendar time. On each new Linux boot, initialize Linux wall-clock to January 1, 1970 00:00:00 UTC plus current Linux uptime, **even if TWRP inherited a plausible-looking but untrusted date**. Show UTC+0 in 24-hour format until verified NTP success; the shared Time Sync status, **NOT year 1970**, indicates whether the clock is uptime fallback or verified NTP time. Only Time Sync policy may change the wall clock. A minimal early helper may be needed to apply fallback before other consumers, but does NOT launch an additional Time Sync service. This supersedes historical conflicting statements about preserving plausible RTC/manual dates or treating 1970 as the authority. See [canonical register](R22D4Q-TIME-SYNC-AUTHORITATIVE-DECISION-REGISTER-2026-10-15.md). No implementation or flash.

> **AUTHORITATIVE CORRECTION (2026-10-15):** The user has explicitly **rejected**, rather than deferred, restoring *any prior system-time values* from SD. The agreed fallback is **1970-01-01 00:00:00 UTC+0 plus elapsed time from the recorded Linux startup**, shown in 24-hour format while unsynced—not a reset to 00:00 when TWRP/Toolkit UI launches. SD saves only user time preferences. Any old discussion of SD last-known-time restoration below is invalid as a release requirement. [Decision register](R22D4Q-TIME-SYNC-AUTHORITATIVE-DECISION-REGISTER-2026-10-15.md).

> **LATEST EVENT-DRIVEN REVISION (2026-10-15):** Time Sync remains permanently **Autoload+Autorun**, but **does not wait for Wi-Fi readiness for any bounded interval**. It starts fallback and watches established network state nonblockingly. **Every actual new transition into `WIFI_READY`**, at boot, after manual Wi-Fi start, or after reconnection, asynchronously triggers a fresh bounded NTP attempt (deduplicate repeated READY reports; serialize jobs). If Wi-Fi is absent, disabled, failed or never connects, retain fallback without blocking startup. NTP request timeout still applies. If a later refresh fails after a successful sync this boot, preserve `xoom.time.synced=1` as a truthful prior success while separately reporting last-attempt failure. [Current Time Sync responsibilities and Wi-Fi event contract](R22D4Q-TIME-SYNC-PACKAGE-RESPONSIBILITIES-AND-SD-PREFERENCES-SPEC-2026-10-15.md). **Design only; not implemented or flashed.**

> **MOST RECENT STARTUP DECISION (2026-10-15):** The Time Sync package is to have **permanently enabled Autoload and Autorun**, invoked by the existing Toolkit boot worker after Wi-Fi; there is **no separate Time Sync launch hook**. Time Sync performs a bounded readiness wait for Wi-Fi, checks SD-owned user time preferences during its normal run, performs one bounded sync attempt, applies preferred display settings on success and advertises `xoom.time.synced=1` only after clock validation. A small frontend user-edit save hook still remains necessary; it is not an auto-launch hook. Keep recovery functioning if the package, SD or network is unavailable. [Package ownership and integration specification](R22D4Q-TIME-SYNC-PACKAGE-RESPONSIBILITIES-AND-SD-PREFERENCES-SPEC-2026-10-15.md). **This is a design decision only; installed R22d4p remains Autoload ON / Autorun OFF for Time Sync and has not been modified.**

## Why simplify
The user rejected elaborate clock-confidence machinery and package Run/Start gating without an actual use case. Keep Linux/TWRP's normal **timekeeping mechanism** intact. **New candidate for discussion (2026-10-15):** When, and only when, recovery has genuinely invalid/default year-1970 time, consider setting the EXISTING kernel wall clock **once** to midnight on that 1970 date, aligned to recovery-session start, so its advancing time-of-day approximates session elapsed time. This revises the previous 'display-only uptime; never adjust the wall clock' preference, but is **conditional on checking real TWRP/ARM behavior first**. It is not an instruction to overwrite any valid clock.

## Only the immediately needed behavior
1. **Wi-Fi Runtime first**, if its saved Autoload/Autorun flags allow it. It has no time prerequisite and should attempt normal connection promptly. Missing card/profile/network does not block recovery or other modules.
2. **Time Sync next** via existing Toolkit boot worker, with permanently enabled Autoload/Autorun in the future revision (no separate launch hook). Its own startup run checks SD time preferences and initializes fallback immediately **without a timed or blocking Wi-Fi wait**. Every distinct new Wi-Fi `WIFI_READY` transition dispatches a fresh one-shot **bounded NTP** attempt asynchronously. If Wi-Fi is off or unavailable, fallback remains; later manual connection triggers a sync. Current R22d4p unchanged (Autoload ON / Autorun OFF).
3. **Announce actual synchronization openly:** Time Sync should publish one simple, documented, machine-readable RAM/Android property, provisionally `xoom.time.synced=1`, **only after NTP success, the OS time update has completed and current system UTC is plausibly validated**. Otherwise property remains `0` (unset explicitly at beginning of each recovery boot). Could preserve existing descriptive `xoom.n2.time.sync` for user messages. No cross-reboot success inheritance from SD.
4. **No periodic per-package polling, elaborate central time service, or synchronized fanout needed.** Future packages simply read `xoom.time.synced` if they care; the existing package manager does not start preventing Run/Start/Load based on time. One flag can be read any time; packages loaded after sync don't miss an event. Diagnostic/export code can label `UNSYNCED` and avoid fabricated date.
5. **Agreed unsynced fallback:** Initialize existing Linux wall clock once per Linux boot to **January 1, 1970 00:00:00 UTC plus elapsed time since the Linux boot**, irrespective of a plausible inherited RTC/TWRP date; 24-hour display at UTC+0. Do not restart uptime at GUI entry or after verified NTP. The **sync status**, not the year 1970, is the authoritative indication of fallback vs real calendar time.
6. **Timestamped reports:** If unsynced, avoid claiming report was captured at 1970 or at a real calendar UTC; record e.g. `time_status=UNSYNCED`, `recovery_elapsed_seconds`, and collision-safe non-date filenames. After actual synchronization, use normal UTC timestamps with `time_source=NTP`. Do not retroactively change old reports.


## NEW proposal awaiting hardware/source validation — initialize invalid wall clock to 1970 midnight
- Objective: in an **unsynced, genuinely invalid** recovery session, provide predictable running hours/minutes/seconds from entry while keeping year 1970 as an unmistakable *invalid calendar-date* cue. This is **not** a 24-hour format setting in the Linux clock; format is UI presentation. The kernel wall clock is absolute epoch time, and advancing across midnight inevitably changes the day (still in 1970).
- Only apply one bounded clock adjustment during early boot, after verifying whether TWRP's built-in time-fix/RTC already established a plausible time and before any NTP/manual correction. A later successful NTP should set real UTC normally; publish `xoom.time.synced=1` **only after verified success**. No repeated resets, day-wrap rewinds, or periodic wall-clock manipulations.
- The exact start reference must distinguish recovery-session entry vs kernel uptime: if TWRP begins minutes after Linux kernel boot, deriving elapsed recovery time from unoffset `/proc/uptime` could misreport it. Use a session-start monotonic anchor if needed.
- Previous issue: the header could show a previous-day clock-time from the configured timezone. The new proposal applies UTC+0 **temporarily while unsynced** to avoid that, preserving the user's actual preferred timezone separately. Explicitly test selected timezone, DST and previously observed missing tzdata warning. Never silently change the user's configured timezone.
- Important side effects to test: backwards wall-clock jump at initialization, filesystem/log mtimes, timeouts (use monotonic for elapsed operations), preexisting persistent timestamps, 32-bit/time_t epoch constraints, and any TWRP internal clock adjustment that might run later. Changing invalid wall clock is only acceptable if it does **not** regress recovery functions.
- A year-1970 date is a **sentinel of invalid calendar time**, not positive proof of the NTP state. `xoom.time.synced=0` means no verified NTP this boot, even if the kernel clock was manually set or plausibly set by an RTC. `xoom.time.synced=1` only after verified Time Sync.
- **Fallback:** If source/hardware tests reveal adverse effects from writing the wall clock, keep stock 1970 timekeeping and display labeled monotonic session uptime in the Toolkit instead. No requirement for unnecessary kernel time rewrites.

## Proposed temporary UTC+0 timezone policy (user refinement, 2026-10-15)

**Status: accepted for design review, subject to recovery-specific timezone implementation verification; not implemented or flashed.** The user proposes deliberately displaying **UTC+0 while `xoom.time.synced=0`**, so an invalid year-1970 clock initialized to `00:00:00` reads as a session-relative timer without timezone offsets, and **restoring the user's preferred timezone after verified NTP sync**.

**Store two separate values (SD file authoritative for preferred settings):**
- **Preferred timezone**: user's actual saved TWRP timezone selection, with DST/offset representation as supported by this recovery. Persist separately and atomically under `/external_sd/XoomToolkit/config/` (provisional `recovery-timezone.conf`, plain text, validated; never put it into Wi-Fi credentials). Keep an in-RAM copy and never overwrite saved preference when applying temporary UTC+0. If SD is missing/read-only, use this-boot RAM preference only if explicitly user-confirmed; otherwise treat preferred timezone as unknown. Report unsaved changes clearly; never treat stock TWRP defaults as an established user preference.
- **Effective timezone**: what TWRP currently uses to format the displayed clock. While no successful Time Sync in this boot, prefer an effective timezone of UTC+0, **without changing the saved preference**. On verified Time Sync success, switch effective timezone to the saved user preference. The Linux wall clock continues to hold UTC epoch time; timezone adjustment is a display/formatting transformation, **never an arithmetic offset added to the epoch**.

**Startup:** restore the preferred timezone from the authoritative SD config if available; do not treat stock TWRP default as user preference. Then temporarily apply UTC+0 without modifying preferred SD data. The one-time 1970-midnight reset is still conditional on genuine clock invalidity, not just absence of NTP. Even if an RTC or manual intervention established a plausible wall clock without NTP, never erase it; the temporarily UTC-format rule and unset sync flag can still hold until successful sync, but a manual future feature may call for an explicit different policy.

**Sync success:** bounded NTP updates kernel UTC, then verify actual system time, attempt preferred-timezone restoration, and publish the current-boot synced flag only after successful clock update (regardless of whether the timezone display restoration itself had an error, which must be separately reported). Avoid a user-visible intermediate state claiming synchronized local time while the preferred timezone has not been applied. When restoration fails, keep the correct UTC clock and display UTC with a visible timezone-warning; do not falsely mark NTP failure.

**Sync failure/offline:** leave the existing kernel wall clock advancing, keep `xoom.time.synced=0`, effective timezone UTC+0, and preferred timezone intact on SD. Offline package loading and Run/Start remain unrestricted. Display explicitly `SESSION` or `UNSYNCED` rather than a believable local clock.

**Recovery environment constraints / required preflight:** R22d4p already emitted `__bionic_open_tzdata` warnings for both `UTC0` and the preferred-looking `CST6CDT,M3.2.0,M11.1.0` form; this means effective libc/TWRP timezone support must be **proven** before relying on `TZ=UTC0` or arbitrary IANA names. Inspect existing timezone controls, TWRP settings persistence, process environment and GUI formatting. If the legacy timezone backend cannot cleanly apply UTC0, explicitly format the unsynced header as UTC without corrupting the global preferred selection; restore the supported format after sync. Test cold boot with SD available/missing, preference changed while unsynced, timezone/DST changes, NTP failure/success, power cycle, and whether system/file timestamps remain UTC-consistent.

**Important:** elapsed recovery-session time should still be derived/verified from a monotonic session anchor when accuracy across boot transitions or late recovery startup matters. A 24-hour wall clock will roll over at midnight; keep year 1970 as an unsynced marker, never pretend time-of-day is accurate actual time.

## Current agreed persistence ownership — Toolkit SD card, NOT TWRP settings file (2026-10-15)

**User correction / decision:** The Xoom's recovery has repeatedly lost time and timezone across recovery sessions. TWRP may contain a persistent-settings API, but that does **not** prove its storage is working or mounted reliably on this device. **Treat /external_sd/XoomToolkit/ as the authoritative persistence store for every preference the custom Toolkit/recovery extensions promise to retain.** Do not use TWRP's built-in persistence as the source of truth. Its GUI and DataManager remain useful for interaction and applying the effective settings in RAM. This decision **supersedes** any earlier text suggesting the TWRP persistent settings file should be preferred or copied as proof of user choice.

**Proposed minimal SD structure (name/schema subject to code review):**
`/external_sd/XoomToolkit/config/time-preferences.conf`
- versioned, validated record for user-confirmed `preferred_timezone`, `gui_timezone_selection`, `gui_timezone_offset`, `gui_timezone_dst`, and `preferred_24h_display`. Only store additional settings after verifying they exist and require persistence. This is **preference storage**, not an attempt to preserve or restore the actual clock date/time.
- Safe write via temp-file, verify and rename with appropriate FAT32 limitations; make failure or missing/read-only SD explicit. SD is a standard Toolkit dependency, but **core recovery must continue operating without it**.

**Initialization sequence and first-run migration:**
1. After mounting the external SD, read and validate `time-preferences.conf` **before the boot worker attempts Wi-Fi and Time Sync and before any backend timezone override**. Preference loading is short and bounded, not dependent on network.
2. If a saved record is present, populate the TWRP GUI's selection/DST/offset/clock-format controls from it and retain an in-memory **preferred** copy. Temporarily display UTC+0 (and session-time format) while unsynced. Do not write this temporary value to SD or to TWRP's persisted `tw_time_zone`.
3. If no record exists (first install, missing file, corrupted file, or no SD), **do not mistake a TWRP default like CST6CDT for the user's actual choice**. Use an explicit unknown-preference state and a neutral temporary UTC+0 display. Present a nonblocking invitation to choose timezone/display preferences when convenient; normal recovery, Wi-Fi and Time Sync remain usable. On Time Sync success, keep UTC display until the user establishes a preference; do not fake a preferred timezone.
4. When the user presses **Set Time Zone** in the frontend, validate and atomically save the selected zone, offset and DST as the **preferred** configuration. When the user changes 12h/24h display setting, save it immediately via a narrow user-facing hook. Other user-configurable time preferences use the same frontend-triggered save behavior if confirmed in the actual custom theme. A change in `tw_time_zone` initiated by the backend must NEVER update preferred settings.
5. When sync succeeds, restore the saved preference to the effective UI timezone/format and publish `xoom.time.synced=1` only when the wall clock was actually updated and validated. Do not make NTP success contingent on finding a preference file: if missing, display correct UTC and report preference is unset.
6. If SD is absent or read-only at a user edit, apply the choice for this session in RAM, **show UNSAVED**, and provide a retry/save action on remount. Never tell user the preference will survive reboot unless a disk readback or equivalent success verifies it.
7. Always keep **preferred settings** and **current temporary backend settings** separate. On the next reboot, only the former should survive. Define what a **Reset Preferences** action does distinctly from TWRP's stock Reset Defaults to avoid accidental erasure. Save current preferred record only from explicit user commit/reset, never from generic variable-change observers.

**Why there was confusion:** The upstream TWRP 3.1.1-era sources have a `DataManager::SaveValues` persistence method. This only establishes an implementation facility, not correct operation on the custom Xoom's selected settings-storage path. Observed failure to retain timezone/preferences warrants removing reliance on it. The 1970 system time is additionally affected by clock/RTC behavior, so don't claim restoring the TWRP settings file by itself would solve date/time.

**Validation before coding:** Verify the actual Xoom SD mount and boot-worker ordering; user-facing timezone commit action (`setguitimezone`), time-format control, timezone/tzdata application, and the verified SD config write/read cycle across two true recovery boots. Never derive the first preferred timezone from an unchanged generic TWRP default.

## Preference ownership: user GUI changes versus backend runtime overrides (2026-10-15)

**Agreed design principle:** The user's preferred time settings are written to the **Toolkit SD configuration** by **explicit frontend user changes**, not through an assumed reliable TWRP settings file. Temporary backend adjustments (e.g. forcing effective UTC+0 and displaying unsynced session elapsed time) **never update the saved preference**. This extends to **all user-configurable time-related settings**, not just the selected timezone.

**Verified upstream TWRP 3.1.1-era code evidence** (TeamWin/android_bootable_recovery branch `android-7.1`, not yet independently verified byte-for-byte in our custom R22d4p binary):
- `gui/action.cpp` `GUIAction::setguitimezone()`, lines 721–743: directly invoked from the user-facing **Set Time Zone** action, reads `TW_TIME_ZONE_GUISEL`, `TW_TIME_ZONE_GUIOFFSET`, `TW_TIME_ZONE_GUIDST`, constructs `TW_TIME_ZONE_VAR`, and calls `DataManager::update_tz_environment_variables()`. This is a concrete **user-commit hook**; do not infer intent by listening to changes in the final timezone variable.
- `data.cpp` `mPersist` already holds timezone selection/offset/DST, effective preferred timezone and `tw_military_time` (12h/24h). `DataManager::LoadValues()` loads a backed settings file; `SaveValues()` persists it to the chosen settings-storage path; `DataManager::SetValue()` distinguishes persistent versus ephemeral variables. `update_tz_environment_variables()` sets the process TZ, calls tzset and writes `persist.sys.timezone`. Need inspect which path our customized Xoom actually uses.
- `tw_military_time` is a persisted user-facing clock-format preference, not a requirement on the wall clock. Verify the corresponding **General Settings 24-hour clock toggle** in the current native theme before hooking; generic `DataManager::SetValue()` does not itself prove the change came from a physical GUI user.
- Searchable original upstream source links: https://github.com/TeamWin/android_bootable_recovery/blob/android-7.1/gui/action.cpp and https://github.com/TeamWin/android_bootable_recovery/blob/android-7.1/data.cpp

**Implementation preference**:
1. On first boot after upgrade, read the **Toolkit-owned SD time preference file** before temporary override. If absent, mark user preference unset; never auto-save or silently infer a deliberate choice from TWRP's generic defaults. Time Sync may proceed before user preference entry, retaining correct UTC display until the user saves a timezone.
2. When user taps **Set Time Zone**, use that action boundary (after successful application) to atomically store on SD the preferred timezone plus selection/offset/DST. An exploratory selection without committing does not replace the prior preference. For 12h/24h toggle, save at the corresponding GUI interaction, not from a background observer of all settings changes.
3. Other user-configurable time preferences that actually exist in our R22d4p UI get the same **user-action → save preference** treatment, subject to a source inventory. Do not mistake clock value itself, synchronizing NTP, or internal 1970-midnight boot adjustment for user *preferences*; these are transient time values, not an enduring timezone/display choice.
4. While unsynced, **backend applies effective UTC+0 and (if desired) 24-hour session display using runtime-only overrides**. Prefer not to call `DataManager::SetValue(TW_TIME_ZONE_VAR, "UTC0")` or toggle `tw_military_time` in `mPersist`, because those are persistent and may overwrite what the user wanted. Review actual TWRP process TZ/header behavior before deciding whether runtime `TZ=UTC0`, `tzset()` and native UI override are reliable. Do not alter chosen DST rules.
5. On a verified network synchronization, restore preferred timezone and normal clock-format preference, leaving Linux epoch time in UTC. If timezone restoration fails, maintain correct UTC and show a timezone warning, not an NTP failure.
6. User adjusts preference while still unsynced: save the newly committed preference immediately but retain the temporary UTC+0 unsynced display until sync, so the user choice becomes effective on success. For direct actions like 12h toggle, decide whether immediate preview should reflect the desired format or whether session-uptime format should remain active; don't silently persist backend format overrides.
7. If SD missing/read-only during GUI changes, preserve the new choice in RAM and clearly report UNSAVED; let user retry once SD becomes available (without background polling). Keep the OS recovery operational offline and without SD.
8. On boot or reset-defaults, correctly identify the user's **persisted** selection and any explicit GUI **Reset to Defaults** action. Never assume all setting changes come from physical GUI or overreact to direct ADB/script modifications. Investigate and make reset behavior consistent with existing TWRP settings if required.

**Preflight required before any code**: confirm actual custom theme's time-related settings, GUI actions, SD mount order versus early worker execution, reliable Toolkit SD file read/write and timezone-data warnings. Inspect `TW_SETTINGS_PATH` only to understand interactions, **not** to rely on it as the preference store. Keep added hooks narrow; do not install a broad DataManager change observer or a new general settings daemon.

## Specifically deferred to future updates, not R22d4q
- **Retroactive timestamp correction** using same-boot monotonic event deltas. Research preserved in [the earlier detailed design](R22D4Q-CLOCK-TIME-CONFIDENCE-AND-SAME-BOOT-RETROCORRECTION-DECISION-2026-10-15.md), but never silently modify old reports now.
- **REJECTED outright:** saving/restoring past system time from SD, boot-time historical checkpoints or using previous-session timestamps to establish/validate the calendar clock. **DEFERRED:** three-state UNSET/ESTIMATED/SYNCED confidence manager and additional manual date/time features beyond existing TWRP functionality.
- **General-purpose time-based package Run/Start gating and `SET TIME`/ `SYNC TIME` statuses.** These are preserved as ideas, not features to build without a concrete package that legitimately requires them.
- Separate persistent hostname and optional mDNS still earmarked for next package-development round.
