# Network Identity / Recovery Hostname — final feature-design handoff
**Design conversation status:** Core intended behavior AGREED and ready for implementation planning (2026-10-15); engineering questions and explicit edge cases remain recorded below. **Nothing implemented, enabled, flashed, or changed on the installed Xoom R22d4p.** This handoff takes precedence over earlier speculative or superseded passages in the longer [Network Identity and mDNS roadmap](NEXT-PACKAGE-ROUND-NETWORK-IDENTITY-AND-MDNS-ROADMAP-2026-10-15.md).

## Settled behavior

1. **Default name:** Deterministic `xoom-recovery-` plus six lowercase hexadecimal characters generated from the recovery-visible 16-hex-character `ro.serialno`. Use the tested inexpensive FNV-1a-style **nibble** XOR/multiply 32-bit arithmetic mixer (initial 2166136261, XOR with hex nibble value, multiply by 16777619 with 32-bit mask per nibble, display low 24 bits in six hex digits). This is not a cryptographic hash or guaranteed globally collision-free. Live hardware sample: `xoom-recovery-87d89c`. One full serial fetch ~0.62–0.63s; arithmetic ~0.01s. [Live measurements](QA-NETWORK-IDENTITY-SERIAL-HASH-BENCHMARK-XOOM-2026-10-15.md).
2. **Name source and storage semantics:** At recovery startup, apply the **saved custom hostname** if present; otherwise compute and apply the default. **Startup initialization alone must not save a new custom preference**. The custom name is stored under `/external_sd/XoomToolkit/` separately from Wi-Fi credentials. **An explicitly saved valid custom hostname may be textually identical to the generated default**; no rejection, special clearing, or prohibition. Conversely, the **Restore Default** action deliberately removes the custom preference and applies the generated name. The distinction is **the action**, not string equality.
3. **Live application:** Set & Save validates, applies the actual running **kernel hostname immediately**, and persists the selected name as the SD custom configuration. Show real outcomes: do not claim “saved” when SD write fails. Propagate changed identity to controllable active network components; external router/DHCP/DNS caches may need renewal and must not be represented as immediately updated without proof. Preserve Wi-Fi and running services; do not disconnect unnecessarily.
4. **Single field/button UX:** Existing Network page displays currently active name and editable hostname. **Nonempty syntactically valid input → Set & Save**; **empty input → Restore Default**; merely clearing input doesn't alter system state. An unchanged, valid nonempty value may be saved again harmlessly. Restore Default clears saved custom configuration and applies generated default. Clear contextual success, error, and pending-verification feedback.
5. **Validation:** Accept one RFC-style hostname label of 1–63 ASCII alphanumeric/hyphen characters; begin/end with alphanumeric; normalize case consistently, reject spaces, periods, underscores and invalid input. Invalid nonempty input cannot Set & Save. Network availability check is distinct from syntax and cannot guarantee a name's freedom globally.
6. **Offline:** Allow the user to Set & Save valid hostname when Wi-Fi is unavailable, **after clearly warning up front** that availability could not be verified and a **genuinely confirmed** conflicting hostname will cause automatic reversion to the generated default. Persist pending-verification status across boots. On later Wi-Fi READY, perform a **nonblocking** conflict check. No reply or ambiguous discovery does not prove availability or conflict.
7. **Confirmed collision with an offline-saved custom name:** Restore the running kernel hostname to generated default and **clear** the saved custom override. Record the old value/reason as separate user-viewable status/history so the user can learn why the setting changed after leaving the Network page. Do not require a popup at the old screen. If default itself conflicts, do not loop; report it.
8. **Changes made outside Toolkit:** A **deliberate valid change of the running kernel hostname** through ADB/shell or other recovery tools is intended to be persisted as custom configuration as well, regardless of whether it matches the generated default. Don't require a separate Adopt button or silently replace it with the old saved preference. Startup application and internal refresh are not deliberate changes and must not create/overwrite saved settings. Detecting externally made changes promptly/reliably is an implementation responsibility; an assignment of the **same** kernel string may be unobservable without monitoring the invoking command, which does not justify costly invasive hooks. Show any unsaved/invalid discrepancies.
9. **Scope:** The actual hostname lives with **Wi-Fi Runtime and the existing Network settings page**, not as a separately installed hostname ZIP. mDNS & Service Discovery is a separate future optional package, OFF by default, and must not activate insecure ADB or SFTP by implication.

## User-facing offline confirmation copy — candidate
**Hostname availability not verified** — You can use this hostname now. When Wi-Fi connects, the Toolkit will check for conflicts. If another device is confirmed to be using the name, the Xoom will automatically restore its generated default name and clear the saved custom hostname.

## Unresolved implementation/exception work — do not invent approved answers
- Identify actual **network conflict-detection mechanism** available with current Wi-Fi Runtime, and distinguish a truly positive conflict from stale DNS, mDNS inaccessibility, silence or wrong device. Prove behavior on Xoom and check compatibility with future RFC 6762 mDNS conflict probing. The treatment of connected-but-inconclusive names, detecting a conflict on a future different network, and a collision of the *generated default* are not fully specified beyond truthful status/safe fallback.
- Determine efficient **external kernel-hostname-change observation**, distinguish startup/internal writes, handle rapid changes, invalid values, no-op identical assignments and SD failures; persist the newest valid intentional state without loops.
- Test `getprop ro.serialno` availability/format/fallback, bitwise arithmetic, cross-boot stability, optional serial-privacy limitations and uniqueness properties, and 63-character hostname limits.
- Check `dhcpcd` hostname argument/restart/lease effects, actual kernel-write permissions and active networking in this TWRP version; don't claim immediate router DNS propagation when not demonstrable.
- Choose exact persistence filename and crash-safe custom-setting replacement/removal, pending-validation metadata, and status history; define SD absent/read-only/reinserted behavior in the **separate Toolkit SD-card resilience discussion**.
- Finalize minimal Network Settings layout/help copy and test real header/field/button alignment. No code or flash authorization is implied.

## 2026-10-16: Linux resolver requirement — separate from approved hostname identity

In addition to the settled device hostname design above, physical Node 24/glibc testing exposed a new **Wi-Fi Runtime** responsibility: provision standard `/etc/hosts` and `/etc/resolv.conf` from real DHCP network information, with a tested `single-request` resolver option for A/AAAA query compatibility. The first RAM-only test restored localhost and external lookups; the extended test proved **default dual-stack HTTPS with strict TLS verification**, not just IPv4-only connections. This does **not** change or reopen any settled hostname identity preference behavior, and does not make the optional mDNS package or passive Network Diagnostics a DNS configuration owner.
