# R22d4q — Time Sync ownership, SD-persisted time preferences, and recovery integration
> **LATEST APPROVED SOURCE-OF-TIME POLICY (2026-10-15):** Time Sync is the **ONLY authority** for recovery calendar time. On each new Linux boot, initialize Linux wall-clock to January 1, 1970 00:00:00 UTC plus current Linux uptime, **even if TWRP inherited a plausible-looking but untrusted date**. Show UTC+0 in 24-hour format until verified NTP success; the shared Time Sync status, **NOT year 1970**, indicates whether the clock is uptime fallback or verified NTP time. Only Time Sync policy may change the wall clock. A minimal early helper may be needed to apply fallback before other consumers, but does NOT launch an additional Time Sync service. This supersedes historical conflicting statements about preserving plausible RTC/manual dates or treating 1970 as the authority. See [canonical register](R22D4Q-TIME-SYNC-AUTHORITATIVE-DECISION-REGISTER-2026-10-15.md). No implementation or flash.

> **AUTHORITATIVE CORRECTION (2026-10-15):** Prior system-time/last-known clock restoration from SD is **REJECTED, not a deferred feature**. SD persists **user time preferences only**. The agreed unsynced fallback uses the Linux clock initialized, when its current value is genuinely invalid, to **1970-01-01 00:00:00 UTC plus seconds elapsed since the recorded current Linux boot start**; show UTC+0 and 24-hour clock while unsynced. This is based on **Linux startup time**, not the later TWRP/Toolkit session start. No older saved system clock values are consulted. See [authoritative decisions](R22D4Q-TIME-SYNC-AUTHORITATIVE-DECISION-REGISTER-2026-10-15.md).

> **DECISION HIERARCHY / 2026-10-15:** The [authoritative Time Sync decision register](R22D4Q-TIME-SYNC-AUTHORITATIVE-DECISION-REGISTER-2026-10-15.md) distinguishes **AGREED user direction**, **UNRESOLVED proposals** and **DEFERRED research**. This document includes exploratory or older design text and must **not** be taken as a fully approved implementation checklist. On conflict, follow the decision register; no implementation or flash has occurred.

> **DESIGN AUDIT (2026-10-15):** [Time Sync coherence review and implementation gaps](R22D4Q-TIME-SYNC-DESIGN-AUDIT-AND-REMAINING-DECISIONS-2026-10-15.md). The concept is sound but **NOT fully implementation-ready**. Resolve the one-shot script's reconnection trigger, ready/registration race, native TWRP timezone application, SD preference first-run semantics and timestamp-export scope before building. Historical paragraphs in this document may describe superseded bounded-Wi-Fi-wait or earlier persistence approaches; the linked audit takes precedence. Active R22d4p remains unchanged.

> **LATEST USER DIRECTION (2026-10-15):** **NO timed waiting for Wi-Fi readiness.** Wi-Fi Runtime publishes explicit connection state (`WIFI_READY`, connection failed/disconnected/stopped); Time Sync is always Autoload+Autorun but **does not block boot** waiting for Wi-Fi. It initializes offline fallback immediately, checks the current state and reacts to every actual **new `WIFI_READY` transition**, including later manual connections and reconnects, attempting one bounded **NTP request per new connection**. If Wi-Fi is not autoloaded, disabled, or connection fails, remain in fallback until a later `WIFI_READY` event. Ignore duplicate READY reports. Preserve last **successful-this-boot** sync flag if a later refresh fails, while separately exposing last-attempt failure. No extra Time Sync startup invocation hook; the existing Toolkit worker starts the package and Wi-Fi Runtime's transition can trigger its sync operation asynchronously. This supersedes the earlier bounded Wi-Fi-readiness waiting language below. **Design only, not implemented or hardware-verified.**

> **USER REVISION (2026-10-15):** Treat the Time Sync module's **Autoload and Autorun as permanently enabled**, using the **existing Toolkit boot worker** to invoke it. **Do not add a separate Time Sync startup invocation hook.** Wi-Fi is attempted first; Time Sync runs next, initializes fallback/preference handling without waiting for connectivity, then reacts asynchronously to the current Wi-Fi status or any later real WIFI_READY connection event to perform bounded NTP. An SD/package/network failure must not prevent recovery operation. The frontend still needs an explicit user-change hook to persist timezone and other time preferences; this is **not** a startup hook. Decide the Toolkit UI presentation of the now-required Autoload/Autorun flags before implementation. Details below marked as earlier designs may require reconciliation.

**Status:** Proposed implementation contract for review, reflecting user decisions through 2026-10-15. **Documentation only: no build, package ZIP edit, settings change, installation or recovery flash.** Active installed recovery is R22d4p; deployed Time Sync package is pinned 0.2.1, with manual Run proven and Autorun not yet hardware tested.

## Scope and motivation
R22d4p does **not reliably retain the user's time/timezone across recovery sessions** (observed). The presence of TWRP `DataManager::SaveValues` does not prove persistent settings work on this Xoom, and the wrong clock date also has a separate RTC/init aspect. The user wants Xoom Toolkit's **external SD card** to be the source of truth for all custom preferences promised to persist, including time-related UI selections.

**Engineering rule:** Time Sync **owns the functional specification and implements as much as feasible**: bounded NTP sync, outcome/status flag, restoration of preferred effective timezone after success, and shared SD time-preferences read/write helper logic. A **very small recovery integration** must handle operations which cannot belong to a loadable package: an early unsynced display/clock initializer if tested safe, a frontend interception of *committed* user preference changes even if Time Sync is unloaded, and reading preferred SD settings at the start of the always-autoloaded Time Sync package's run, before it applies user preferences. Do not add a second separate Time Sync startup invocation hook. Avoid two competing implementations or a large clock daemon.

## Responsibility boundary

| Responsibility | Primary owner | Reason |
|---|---|---|
| Kernel/TWRP underlying wall-clock progression | Existing TWRP/Linux | Do not replace an operating-system clock |
| Apply boot-relative unsynced fallback, UTC+0/24h display, and initialization status under Time Sync's authority | Small built-in recovery boot/UI helper | Must initialize at every Linux boot, even when RTC date appears plausible or Time Sync package is unavailable; cannot falsely report ready if it fails |
| Read validated preferred time settings from external SD | Common helper called by automatically started **Time Sync** package before applying timezone | No distinct new startup hook; Time Sync runs via existing Toolkit worker |
| User explicitly commits **Set Time Zone** (zone, DST, offset), clock format (12h/24h), or other confirmed time UI preferences | Existing TWRP GUI action with small Toolkit save hook | Only frontend-committed choices are preferences; backend's temporary UTC override must never overwrite them |
| SD serialization, validation, atomic write, readback and "UNSAVED" outcome | Shared Toolkit time-preferences helper (specified and tested with Time Sync), independent of optional package being loaded | GUI save must work even if Time Sync is disabled/unloaded; share logic rather than copy it |
| Bounded NTP request, checking final kernel UTC, clear success/failure status | **Time Sync package** | Core function of verified installable package |
| Restore user's saved timezone and display choice **after sync** | **Time Sync**, via shared helper and narrow recovery native apply interface | Depends on actual Time Sync completion; avoids applying an arbitrary saved TZ while the display is showing session time |
| Publish post-success signal | **Time Sync** | Property `xoom.time.synced=1` only **after** clock update verified; default/reset to 0 at each recovery boot |
| Boot ordering and connection trigger | Existing Toolkit boot worker plus small Wi-Fi Runtime state-transition integration | Wi-Fi Runtime first, Time Sync second (permanent Autoload/Autorun); a new real WIFI_READY transition triggers Time Sync asynchronously; neither waits for an unresponsive network indefinitely |
| Future time-dependent package blocking, SD history, retroactive timestamp correction | **DEFERRED** | No demonstrated current use case justifying added architecture |

**Important deployment constraint:** A package stored only on external SD cannot be the only implementation of the frontend preference-save hook, because the user must still be able to set time preferences if that package is unloaded. The single shared helper can be delivered with recovery while Time Sync specifies/consumes its API. This is intentional minimal core integration, not a second independent time management system.

## Proposed on-SD configuration
- Authoritative path: `/external_sd/XoomToolkit/config/time-preferences.conf` (exact path/schema to be confirmed against current Toolkit layout).
- Fields: `version=1`, `preferred_timezone=<validated POSIX TZ accepted by THIS recovery>`, `gui_timezone_selection=...`, `gui_timezone_offset=...`, `gui_timezone_dst=...`, `preferred_24h_display=0|1`; include only fields actually supported by the custom theme. No network credentials.
- Authoritative preference comes from **explicit user commits**. **Do not initialize it from generic TWRP defaults** such as `CST6CDT...` on the first boot: those have not been demonstrated to be the user's preference.
- Use validated bounded text parsing; temp file write, flush, rename and readback, with sensible FAT32 interrupted-write safeguards. Never claim saved if media is missing/read-only; keep unsaved value in RAM and show user an explicit unsaved/error status. Don't write from a generic `tw_time_zone` change observer.
- Actual wall-clock date/time and `xoom.time.synced` are **session data**, not persistent settings. Do not store old sync status as if it were valid for a new recovery boot.
- At initialization: if valid file exists, load preferred user choices into the UI controls and **separate RAM preference values**. If absent/invalid, treat preference as unknown, show UTC+0 until the user explicitly chooses, and still let Wi-Fi/Time Sync operate. If NTP succeeds before the user ever saved preferences, show correct UTC time and invite user to select timezone; do **not** automatically declare the TWRP default preferred.
- If an explicitly changed preference is saved while still unsynced, keep displaying temporary UTC+0 until NTP sync completes, then apply the newly preferred TZ. Confirm interaction intuitiveness in theme UX.
- Distinguish `preferred_* (on SD)` from `effective_* (current session)`. Backend changes to effective timezone/format never persist.

## Startup and synchronization contract

1. Recovery boots and mounts SD as available. Existing Toolkit boot worker invokes Wi-Fi Runtime first, then **always** autoloads and autoruns Time Sync. Time Sync invokes the shared preference loader **at the beginning of its run**, without network dependence or unbounded wait. A separate startup launch hook for Time Sync is not needed.
2. **Agreed fallback (irrespective of a plausible inherited date):** At every fresh Linux boot initialize existing Linux clock **once** to January 1, 1970 00:00:00 UTC + current kernel-boot uptime, show UTC+0 and 24-hour format until Time Sync verifies NTP. Ensure fallback initialization precedes all consumers, including if the Time Sync ZIP is absent; status must not claim fallback is valid if initialization fails. Do not use previous SD system times. This operation is part of Time Sync's sole authority, potentially implemented by a minimal built-in early helper.
3. Apply temporary UTC+0 effective display while not successfully synchronized; preserve saved preferred timezone and clock format separately. Need source/hardware test because existing Bionic tzdata warnings were observed.
4. Toolkit worker attempts enabled Wi-Fi Runtime before Time Sync. Time Sync has **permanent Autoload/Autorun** enabled and **does not wait for Wi-Fi as a blocking operation**. When started, it checks current Wi-Fi state and registers/subscribes to new connection transition notifications. On every **new** `WIFI_READY` event it schedules a **bounded** NTP attempt without blocking Wi-Fi Runtime, the boot worker, or unrelated packages. Wi-Fi disabled, uninstalled, offline or failed? Use fallback time immediately, and wait passively for a future READY event if Wi-Fi later starts manually. There is **no timeout for when a connection might become available**; only the NTP transaction has a timeout. The exact event/registration mechanism must be verified against the installed worker and recovery source.
5. On **actual success**, Time Sync sets/validates kernel UTC, uses common helper to get most recent preferred settings (an SD read or up-to-date RAM choice), restores effective timezone/format via the verified native interface, publishes `xoom.time.synced=1`. If restoration fails, NTP UTC stays correct and a separate warning is shown; do not misreport the NTP outcome.
6. On failure with no prior successful sync this boot: keep `xoom.time.synced=0`, effective UTC+0, keep kernel clock running, keep all packages usable. Wi-Fi failure or absence causes fallback and no NTP attempt; a later confirmed connection retries. If a **later refresh** fails after an earlier valid sync, retain `xoom.time.synced=1` as the truthful 'synced at least once this boot' flag, preserve the correct clock and preferred timezone, and separately record `last_sync_attempt=FAILED`/reason/time. A transient refresh failure is not proof the earlier clock correction was undone.
7. No package Run/Start/Load gating and no continuous per-package clock polling in R22d4q. Interested future packages read the simple flag. Reports made unsynced label `UNSYNCED` plus recovery-session elapsed time, not fabricated calendar dates.
8. A new recovery session explicitly resets flag to `0`; there is no cross-boot sync inheritance. A manual direct change to date/time is not represented as an NTP success.

## Wi-Fi-driven synchronization triggers — authoritative event contract

**Why:** Wi-Fi may be deliberately disabled at boot, offline for hours, started manually, or repeatedly disconnected/reconnected. A timeout waiting for readiness would miss later opportunities. The user wants Time Sync to synchronize **on every new network connection** (not on every READY status read), including when already synced.

**Definitions**
- **Connection-established transition**: Wi-Fi's authoritative network state moves from a state other than `WIFI_READY` to `WIFI_READY`, with WPA/DHCP/IPv4 readiness as in currently tested Wi-Fi Runtime. Distinguish it from `xoom.toolkit.wifi.runtime=READY` (only runtime process readiness), which can occur before network is actually usable.
- **Connection ended/failed**: explicit `WIFI_STOPPED`, disconnected, failed-to-connect or equivalent authoritative Wi-Fi outcome. Do not run NTP. Offline fallback remains usable.
- **Per-connection generation**: a unique counter/transition ID incremented on each real not-ready→ready transition this recovery session; needed to ensure exactly one triggered attempt per established connection rather than repeated status repaint. Concrete representation to be determined from actual worker interfaces.

**Time Sync lifetime**
1. Existing autoload/autorun invokes Time Sync at boot, even if Wi-Fi has not connected. It immediately loads saved time preferences and initializes fallback UTC+0/unsynced presentation where applicable; **it does not synchronously wait for Wi-Fi**.
2. A small nonblocking integration ensures Time Sync sees new `WIFI_READY` transitions. Prefer **Wi-Fi Runtime event callback or asynchronous trusted Toolkit manager dispatch** rather than creating a resident polling daemon. Time Sync also checks current state when it becomes available, so a READY event that occurred during package loading is not missed (race solved by generation/processed-ID reconciliation).
3. If no Wi-Fi package, Autoload OFF/Autorun OFF, failure or offline: no new sync job. Time Sync stays ready for a future **manual Wi-Fi start**. Backend and UI remain available.
4. On `WIFI_READY` with a newly observed generation, **schedule** one Time Sync request. Do not execute NTP synchronously inside Wi-Fi's connection transition handler. Enforce one active NTP job; duplicate or overlapping READY events may be collapsed/queued by generation. Each NTP request itself has a bounded timeout. On completed successful NTP, verify system UTC and publish `xoom.time.synced=1`, restore preferred timezone and report outcome.
5. On an NTP failure, leave fallback if never synced, or retain previous valid sync status and preferred display if this session already synced. Show failure separately; allow next real connection to initiate another attempt. There is **no periodic attempt** merely because the connection stays up; the user can still explicitly press Run to retry when needed.
6. If Wi-Fi's failure/stop event occurs while an NTP job is active, allow the bounded request to end/cancel; prevent a stale job from hiding newer connection generations or triggering repeats. Avoid any dependency cycle between Wi-Fi Runtime startup and Time Sync.
7. No requirement to block module loader after Time Sync is loaded. No arbitrary fixed delay before checking sync and no general-purpose package time execution gates.

**Compatibility and limits:** The current Time Sync 0.2.1 is a one-shot script; it does NOT already provide a persistent event receiver or ready-transition interface. The exact minimal Wi-Fi/Toolkit integration (rather than a new launch hook) requires inspecting the source of R22d4p boot worker, network status transitions and module manager. Document these event/API changes in the new **versioned, pinned** Time Sync ZIP and Wi-Fi module/integration revision; do not alter existing hashes in place.

**Tests:** Wi-Fi comes ready before Time Sync loads; Time Sync loads first and then Wi-Fi gets ready; slow/failing network; Wi-Fi not started on boot then manual start; disconnect/reconnect repeated 3 times; repeated duplicate WIFI_READY; rapid reconnect during active NTP; NTP success then failure; Time Sync package unavailable; no SD; recovery UI/USB ADB always responsive.

## Frontend setting-change hooks
**Source anchor (upstream TWRP 3.1.1-era Android 7.1; confirm in custom R22d4p):**
`GUIAction::setguitimezone` in `gui/action.cpp` (TeamWin/android_bootable_recovery, `android-7.1`, lines 721–743) is the explicit user "Set Time Zone" commit: reads `TW_TIME_ZONE_GUISEL`, `TW_TIME_ZONE_GUIDST`, `TW_TIME_ZONE_GUIOFFSET`, updates `TW_TIME_ZONE_VAR`, and calls `update_tz_environment_variables()`. Add the narrow preference-save hook **on deliberate commit**. Do not treat arbitrary backend `DataManager::SetValue` calls as user actions.

`tw_military_time` (12h/24h) is a distinct persisted UI variable in upstream `data.cpp`; locate the real physical GUI toggle and hook the frontend change. Inventory other user-configurable **time** settings before expanding save schema. Avoid automatically persisting backend-imposed 24h unsynced display format. `DataManager::SaveValues` is available upstream but empirically insufficient to trust on this Xoom.

When saving the preferred TZ, also preserve the display/GUI selection, DST flag and offset—not merely the current `TZ` string—so the Settings page reflects the actual choice after a new recovery boot.

## What should be in the Time Sync package's own documentation and ZIP
- Update Time Sync README/manifest documentation for supported recovery revisions, dependencies on common helper interface, result properties, bounded timeouts and preference file schema.
- Preserve the existing 0.2.1 QA reference and ZIP hash as history; never modify the pinned installed ZIP in place. A revised Time Sync ZIP must be new, versioned, hashed, reviewed, and explicitly staged before changing any manifest pin.
- Existing 0.2.1 has a bounded BusyBox NTP query (20 seconds, `162.159.200.1`) and `xoom.n2.time.sync` descriptive property. Add `xoom.time.synced` only after reliable clock validation, with compatibility to existing consumers where feasible.
- Time Sync must *not* own loading the initial preferred setting if it only starts after Wi-Fi: early boot helper must supply that before attempting any synchronization. Time Sync performs the startup preference read and post-sync restoration using the same helper. It is invoked by the existing boot worker with fixed Autoload/Autorun; no new startup launch hook.

## Explicit future backlog, excluded
**DEFERRED:** same-boot retroactive timestamp correction, formal package time requirement / SET TIME blocking, new authenticated time protocol, hostname/mDNS feature round. **REJECTED, not deferred:** any persistence, checkpoint restoration, or comparison of prior Linux calendar times on SD as fallback. SD is reserved for persistent **user preferences** (timezone, DST, clock format), not historical clock values.
