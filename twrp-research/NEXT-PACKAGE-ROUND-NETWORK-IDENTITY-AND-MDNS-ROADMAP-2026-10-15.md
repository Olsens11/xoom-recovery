## APPROVED default hostname generation — lightweight serial mixer

**User-approved decision (2026-10-15):** Use `xoom-recovery-` plus a **six-character lowercase hexadecimal suffix** derived deterministically from the device's recovery-visible `ro.serialno`. Mix **all 16 hexadecimal serial nibbles**, not a directly exposed contiguous substring or a sparse sample. Use the **already hardware-tested FNV-1a-style nibble XOR/multiply mixer**, requiring only existing shell builtins, rather than launching SHA-256. The output is a convenience device identifier, not a secret or cryptographically irreversible serial protector; collisions remain possible.

**Frozen candidate arithmetic** (exact byte/format details to pin in implementation tests): initialize 32-bit state to `2166136261`; for each hexadecimal nibble in the normalized lower-case 16-character serial, XOR with the nibble's numeric value, multiply by `16777619`, and mask to 32 bits. Format the lower 24 bits of the final state as six lowercase hexadecimal digits (leading zeros retained). The *nibble* treatment distinguishes this from canonical bytewise FNV-1a. Verified example from the connected Xoom: `xoom-recovery-87d89c`.

**Live recovery performance:** Three raw serial lookups took ~0.62–0.63 s each. The all-16-nibble arithmetic took ~0.01 s or less at the available resolution, without another hash executable. SHA-256 took 1.01 s end to end under different load and a high-count executable-launch stress test caused excessive system load; avoid repeating that stress pattern. [Hardware benchmark and controls](QA-NETWORK-IDENTITY-SERIAL-HASH-BENCHMARK-XOOM-2026-10-15.md).

**Still engineering/UX questions, not permission to implement:** confirm serial input/normalization and error/fallback when missing or malformed; ensure stable output across boots; generate/cache only when needed, never on every Wi-Fi reconnect, DHCP renewal or page redraw; enforce sane host-label validation and collision handling when mDNS later exists. A saved **custom hostname** takes precedence over the generated default, even when the two strings are identical. **No custom setting** means compute the default without saving it. No current recovery setting or hostname was changed.

> **APPROVED HOSTNAME EDITOR UX (2026-10-15):** Reuse **one button next to the editable hostname field**. When the field contains text, its action/label is **`Set & Save`**; when the field is empty, it changes to **`Restore Default`**. Merely erasing text never changes the live hostname. Explicit Restore Default should clear the user's persistent custom override and apply the stable device-specific generated default; report unsaved/failed state if persistence fails. Native page fit and storage error handling await implementation. No changes have been deployed.

> **OFFLINE NAME CONFIGURATION AND LATER CONFLICT RESPONSE APPROVED — 2026-10-15:** A syntactically valid hostname can be applied/saved offline, but warn **at the moment of offline Set & Save**: availability has not been verified and **a confirmed later conflict will automatically restore the generated default hostname**. Keep a persistent pending-validation marker across recovery boots so the deferred check is not lost. When Wi-Fi connects, check asynchronously; if a genuinely different device is established to be using the name, switch the active kernel hostname to generated default and **clear the saved custom hostname override on SD**; do not save the default as configured. Leave the name unchanged if conflict status is unknown or inconclusive. Show the reason in Network settings/history when the user returns, without requiring them to still be on the hostname page. Default-name conflicts and out-of-band hostname persistence need separate handling. No implementation, setting change or flash has been authorized.

## Approved live hostname/persistence policy and name-validation work (2026-10-15)

**Configuration invariant:** `configured = saved custom hostname OR no saved custom hostname`. An explicit Set & Save stores the valid entered string **regardless of equality with the generated default**. With no saved custom name, the default is computed from hardware. An explicit Restore Default or confirmed-conflict fallback clears the saved custom name. Merely initializing/reapplying a generated hostname on boot does not save it. Conflict history is separate diagnostic metadata.


**New explicit user decision:** A successful **Set & Save** applies a validated hostname immediately to the running recovery and stores the text as the configured custom hostname on Toolkit SD—even if identical to the generated default or currently active name. The saved custom value remains authoritative across boots until overwritten by another valid save or explicitly **cleared** by Restore Default or a confirmed offline-name conflict. Routine startup generation does not itself create a custom setting. This applies to the real kernel hostname, not just a GUI or Android property. No merely entered/unsaved text changes the live hostname. A failed save must never claim persistent success; report application and save outcomes truthfully and avoid silently desynchronizing them. Confirm the safest ordering/rollback/commit behavior in implementation testing.

**Network application:** Update the live kernel hostname promptly on a successful action. Propagate the new name to advertising/discovery systems if they are running; attempt appropriate DHCP hostname update in a way that avoids unnecessary Wi-Fi or remote-service disconnection, subject to behavior of the Xoom's actual dhcpcd build. **Do not promise that a router's DHCP DNS cache, unicast DNS registration or remote peers all update instantly** merely because the kernel hostname changed. Show distinct feedback if network advertisement must await renewal/reconnection. The broader "take effect immediately" goal applies locally and to any controllable active service, with explicit reporting about external network registration limitations.

**New user requirement:** A custom hostname must be **valid and available** before the UI makes **Set & Save** usable. Treat these as two different checks:
- **Local syntax validation:** normalize/reject invalid host label (single hostname label, 1–63 ASCII characters, letters/digits/hyphens, must begin/end alphanumeric; lowercase for consistent presentation; no spaces, underscores, dots, or empty custom name). Invalid candidates cannot enable Set & Save; blank field instead exposes the previously approved **Restore Default** action. **An unchanged but valid nonempty value remains eligible for Set & Save**, with safe idempotent application and persistence; do not reject it for equaling the generated or active hostname.
- **Network availability:** when Wi-Fi is connected, check for currently **observable conflicts** using supported network mechanisms. An existing conflicting DNS or mDNS answer is meaningful, but a silent lookup is NOT proof that the name is globally free; DNS may be stale, mDNS is link-local, clients can be asleep, and optional mDNS responder is part of a later package. Probing and conflict resolution for `.local` should follow RFC 6762 once optional mDNS is developed. Do not claim absolute uniqueness on every network.
- **APPROVED — offline configuration with automatic confirmed-conflict fallback (2026-10-15):** A syntactically valid custom hostname **can be Set & Saved and applied immediately while Wi-Fi is disconnected**. Before the offline save, show a clear notice: **`This hostname cannot be checked while offline. If another device is found using it when Wi-Fi connects, the Xoom will automatically restore its default hostname.`** Acknowledge as part of the explicit Save action. Persist the selected name and **pending network-validation status** on SD so a reboot before connecting does not lose the eventual check. On new Wi-Fi connectivity, run a **nonblocking** conflict check. **Only positive evidence that a distinct device owns/answers for the same network name** should trigger fallback; no DNS response, stale DNS or unsupported probing is NOT proof of availability or a conflict. For a verified conflict, restore the generated device-specific default immediately as active hostname, **clear the custom hostname override from SD without saving the default as configured**, and provide an observable **`Name conflict detected — restored default hostname`** result (include previous attempted name and reason in Network settings/status/history so user who already left the page can discover it). No pop-up requiring the user to remain on the original screen. If persistence of the reset fails, report active/saved divergence explicitly and retry or defer safely; never falsely claim the default was saved. If the **generated default itself** conflicts, report rather than looping auto-resets. Inconclusive checks keep the user choice and show **`Availability not verified`**. Whether connected-but-unverifiable custom names should receive identical deferred-fallback treatment, and whether verified names should reset on conflicts on *other future networks*, remain separate questions.

**APPROVED direction — persist hostname changes regardless of origin (2026-10-15):** The user intends **every deliberate valid change of the recovery's actual system hostname** to persist as a custom hostname, whether made via the Toolkit editor, ADB/shell, or another tool. This includes a custom setting whose value equals the generated default. A validated, observable external hostname change should be detected and recorded on SD for later boots. Only explicit Restore Default or confirmed conflict reset clears the custom setting; normal startup initialization is not a user change. An external command setting the current hostname to the exact same string leaves no observable kernel-value transition; do not add costly monitoring just to distinguish this no-op from a deliberate duplicate save. Do **not** silently revert an intentional external change to the previous saved preference, and do **not** require an extra "Adopt" button. The Network page and Help should state that hostname changes made anywhere in recovery are intended to be saved automatically.

**Important distinctions for implementation (NOT license to override intent):**
- Observe the **actual running kernel hostname**, not just writes to the Toolkit field or an Android property. The specific reliable low-overhead observation mechanism is an **engineering test**; source-independent detection may require a small resident watcher and reconciliation at controlled lifecycle points. Do not falsely promise instantaneous persistence of an ADB change before the observer actually detects it. Treat **the newest deliberate, valid hostname change** as authoritative and avoid race/stale-save overwrites.
- The native recovery/Toolkit applying the generated default or restoring an already saved name at **startup** is internal initialization, **not a fresh user-intended change** and must not overwrite saved configuration. Likewise, automatically reapplying the current saved value must not trigger another write loop.
- The separately approved **offline-name conflict reset** is an intentional Toolkit policy exception: once a *confirmed* collision causes a return to generated default, the default becomes the active hostname and the **custom configured override is cleared**; separately record the previous attempted name and reset reason as diagnostic history.
- Retain local hostname **syntax/format validation** before persisting externally applied changes; the kernel may accept strings that are unsuitable as network host labels. If an invalid external value appears, avoid writing it to persistent configuration, truthfully show current versus saved hostname, and surface a validation warning; exact recovery/repair behavior is for engineering/UX review rather than silently adopting an invalid persistent name.
- With missing/read-only SD, do not claim the change was saved. Keep active state and show **UNSAVED**, with reconciliation after SD returns subject to the separate SD-removal resilience discussion.
- An mDNS responder using an alternate **advertised conflict-resolved name** does not necessarily change the kernel hostname; only an actual intentional system-hostname change triggers this persistence rule.

**Suggested Network page notice:** "Hostnames set in recovery are saved automatically, including changes via ADB or other tools. Restore Default clears the saved custom setting. You may also save the default name as a custom value." Show actual save failures and pending network conflict validation clearly.

**Implementation boundary:** These are design decisions and questions, not authorization to modify/flash the currently running recovery. The existing hostname is unchanged.
