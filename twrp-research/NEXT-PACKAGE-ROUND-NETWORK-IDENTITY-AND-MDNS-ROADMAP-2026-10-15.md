## APPROVED default hostname generation — lightweight serial mixer

**User-approved decision (2026-10-15):** Use `xoom-recovery-` plus a **six-character lowercase hexadecimal suffix** derived deterministically from the device's recovery-visible `ro.serialno`. Mix **all 16 hexadecimal serial nibbles**, not a directly exposed contiguous substring or a sparse sample. Use the **already hardware-tested FNV-1a-style nibble XOR/multiply mixer**, requiring only existing shell builtins, rather than launching SHA-256. The output is a convenience device identifier, not a secret or cryptographically irreversible serial protector; collisions remain possible.

**Frozen candidate arithmetic** (exact byte/format details to pin in implementation tests): initialize 32-bit state to `2166136261`; for each hexadecimal nibble in the normalized lower-case 16-character serial, XOR with the nibble's numeric value, multiply by `16777619`, and mask to 32 bits. Format the lower 24 bits of the final state as six lowercase hexadecimal digits (leading zeros retained). The *nibble* treatment distinguishes this from canonical bytewise FNV-1a. Verified example from the connected Xoom: `xoom-recovery-87d89c`.

**Live recovery performance:** Three raw serial lookups took ~0.62–0.63 s each. The all-16-nibble arithmetic took ~0.01 s or less at the available resolution, without another hash executable. SHA-256 took 1.01 s end to end under different load and a high-count executable-launch stress test caused excessive system load; avoid repeating that stress pattern. [Hardware benchmark and controls](QA-NETWORK-IDENTITY-SERIAL-HASH-BENCHMARK-XOOM-2026-10-15.md).

**Still engineering/UX questions, not permission to implement:** confirm serial input/normalization and error/fallback when missing or malformed; ensure stable output across boots; generate/cache only when needed, never on every Wi-Fi reconnect, DHCP renewal or page redraw; enforce sane host-label validation and collision handling when mDNS later exists. User-entered explicitly saved hostname takes precedence over generated default. Exact persistence semantics for the *generated default* and user customization remain to be discussed. No current recovery setting or hostname was changed.

## Approved live hostname/persistence policy and name-validation work (2026-10-15)

**New explicit user decision:** A successful **Set & Save** sets the **actual running recovery hostname immediately**, and records that selected hostname to the Toolkit SD card as the configured hostname for subsequent recoveries. The configured hostname remains authoritative across boots until deliberately replaced by a later successful custom Set & Save or the already-approved **Restore Default** action. This applies to the real kernel hostname, not just a GUI or Android property. No merely entered/unsaved text changes the live hostname. A failed save must never claim persistent success; report application and save outcomes truthfully and avoid silently desynchronizing them. Confirm the safest ordering/rollback/commit behavior in implementation testing.

**Network application:** Update the live kernel hostname promptly on a successful action. Propagate the new name to advertising/discovery systems if they are running; attempt appropriate DHCP hostname update in a way that avoids unnecessary Wi-Fi or remote-service disconnection, subject to behavior of the Xoom's actual dhcpcd build. **Do not promise that a router's DHCP DNS cache, unicast DNS registration or remote peers all update instantly** merely because the kernel hostname changed. Show distinct feedback if network advertisement must await renewal/reconnection. The broader "take effect immediately" goal applies locally and to any controllable active service, with explicit reporting about external network registration limitations.

**New user requirement:** A custom hostname must be **valid and available** before the UI makes **Set & Save** usable. Treat these as two different checks:
- **Local syntax validation:** normalize/reject invalid host label (single hostname label, 1–63 ASCII characters, letters/digits/hyphens, must begin/end alphanumeric; lowercase for consistent presentation; no spaces, underscores, dots, or empty custom name). Invalid candidates cannot enable Set & Save; blank field instead exposes the previously approved **Restore Default** action. Unchanged value can be treated as no-op.
- **Network availability:** when Wi-Fi is connected, check for currently **observable conflicts** using supported network mechanisms. An existing conflicting DNS or mDNS answer is meaningful, but a silent lookup is NOT proof that the name is globally free; DNS may be stale, mDNS is link-local, clients can be asleep, and optional mDNS responder is part of a later package. Probing and conflict resolution for `.local` should follow RFC 6762 once optional mDNS is developed. Do not claim absolute uniqueness on every network.
- **APPROVED — offline configuration (2026-10-15):** A syntactically valid custom hostname **can be Set & Saved and applied immediately even with Wi-Fi disconnected**. When no network check can be performed, show **`Availability not verified`** (or equivalently explicit wording) rather than claiming that the hostname is unique or free. Persist the selected hostname to the Toolkit SD, subject to actual save success, and use it as configured on subsequent recovery boots. **When Wi-Fi later becomes ready, perform an appropriate nonblocking conflict check** and report any detected conflict. Do not block recovery, revoke a successfully saved preference, or automatically rename the Xoom just because verification was unavailable; the precise UX/resolution of a detected conflict is still for separate discussion. A connected network with inconclusive results must also remain explicitly **unverified** rather than being treated as proven available.

**Another explicit open question:** An externally imposed hostname change (e.g. via USB ADB / shell / another package) can make **current live hostname** differ from the **saved configured hostname**. It is **not agreed** whether to persist such changes. Recommended starting policy for discussion: **do not automatically save out-of-band changes** (they could be transient diagnostic actions); instead display current versus configured hostname and offer explicit user action to adopt a different name or reapply the configured name. The configured value remains the boot-time preference until the user intentionally changes it through Toolkit. Avoid overwriting an external change silently during an active recovery session without agreed policy.

**Implementation boundary:** These are design decisions and questions, not authorization to modify/flash the currently running recovery. The existing hostname is unchanged.

3. **Next package development round, phase A: persistent hostname / Network Identity.** The hostname is not a separate installable ZIP. Integrate its logic with **Wi-Fi Runtime** and the existing **Network** page:
   - Show current recovery hostname and an editable hostname field with **one context-sensitive button beside it**. **Non-empty input → `Set & Save`** (validate and apply/save the custom hostname); **empty input → `Restore Default`** (on deliberate button press, restore the deterministic `xoom-recovery-<6hex>` generated hostname, remove the custom-name override from saved preferences, and apply the default). Clearing the field alone changes the button label **but does not modify the live or saved hostname**. Following successful restore, populate the field with the restored name. Show current/effective and saved values and clear success/failure feedback. Provide validation (single RFC-compatible host label, letters/digits/hyphens, no leading/trailing hyphen; choose reasonable length limit); an invalid nonempty field never silently restores the default. If SD is absent/read-only, never claim a custom-name override was cleared persistently.
   - Atomically save a plain-text hostname to an appropriate private dedicated file beneath `/external_sd/XoomToolkit/` (do not put it inside Wi-Fi credentials). Overwrite previous hostname only after successful validation and atomic rename; ensure the value persists across recovery reboots and SD is not silently considered saved if missing/read-only.
   - Apply immediately to **recovery's actual kernel hostname** (current live observed `/proc/sys/kernel/hostname` = `localhost`) on successful Set & Save or Restore Default and persist the user's configured selection to SD. Maintain any relevant Android `net.hostname` property consistency only if verified meaningful for this recovery. Never claim persistence if writing fails; exact transaction/failure rollback sequencing needs implementation testing. Do not modify Android OS `/system` or `/data`, and do not assume that a property alone sets the kernel hostname.
   - Restore on the normal Wi-Fi Runtime **Autorun** path, before DHCP whenever possible; use same saved name on **manual Wi-Fi connect**. Running dhcpcd currently receives `-d -t 25 wlan0` with no explicit hostname, while the packaged dhcpcd supports `-h, --hostname hostname` (inspect exact compatibility before coding). Do not disconnect active Wi-Fi merely to update the local hostname; explain that the DHCP-advertised name may update on next connection/renewal.
   - Do not claim that a kernel hostname by itself makes the Xoom addressable from another device; router DNS and/or mDNS are separate.
4. **Next package development round, phase B: optional mDNS & Service Discovery package.** It should be a **separate, explicitly opt-in pinned and verified Toolkit package**, with Autoload copying/verifying trusted responder payload and Autorun starting it only after Wi-Fi is ready. Both OFF by default initially; no arbitrary SD binaries. Use a lightweight responder compatible with original Xoom ARM ABI/old TWRP userspace. Provide correct multicast UDP 5353 behavior, RFC 6762 hostname claim/conflict handling, and RFC 6763 DNS-SD advertisement.
   - Resolve the saved hostname as `<hostname>.local` for compatible clients on the same LAN (subject to VLAN/multicast and client support). Do not equate mDNS with authoritative global DNS or routing across arbitrary subnets.
   - Advertise **only genuinely running network services**, such as Modern SFTP's SSH service when enabled. Use standard `_ssh._tcp` and potentially `_sftp-ssh._tcp` DNS-SD service types when supported, with actual listening ports; do not start/enable the service merely because mDNS is running.
   - Define stop/unload behavior so responders release resources cleanly and other modules remain operational. Ensure minimal attack surface, no credential broadcast, no automatic anonymous root ADB exposure. Keep insecure wireless ADB POC OFF unless explicitly authorized.
   - Test from Surface Book: hostname.local resolution and disappearance/update, IP changes, hostname conflicts, Wi-Fi reconnects, mDNS start/stop, and service-discovery records corresponding to Modern SFTP state.
5. **Test/release policy:** Do not silently modify active R22d4p or flash a new recovery without explicit approval. Use staged/offline candidates with full-partition p6 backup and independent readback verification for any future recovery write. Test R22d4q UI and future package discovery in separate controlled phases.
