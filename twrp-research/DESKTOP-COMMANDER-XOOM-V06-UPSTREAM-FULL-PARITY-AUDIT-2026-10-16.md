# Xoom Desktop Commander v0.6 — complete upstream tool parity audit

**Audit date:** October 16, 2026. **No package has been built.**
**Upstream reference:** [wonderwhy-er/DesktopCommanderMCP](https://github.com/wonderwhy-er/DesktopCommanderMCP) at Git commit [`f508e524469c26f6366e17dbfd3ee5a69d112127`](https://github.com/wonderwhy-er/DesktopCommanderMCP/tree/f508e524469c26f6366e17dbfd3ee5a69d112127), `package.json` version `0.3.0`, commit October 14, 2026. Actual definitions in `src/server.ts`, `src/tools/schemas.ts`, handlers and engine modules, not assumptions from tool names.
**Xoom reference:** physically accepted [v0.6 candidate and worker](desktop-commander-prototypes/v06/) on MZ600 TWRP R22d4q, [hardware tests and framebuffer assessment](DESKTOP-COMMANDER-XOOM-V06-26-TOOLS-FRAMEBUFFER-INVESTIGATION-2026-10-16.md). This review is a **static semantic contract comparison** backed by the prior Xoom v0.6 physical tests; it is not new cloud acceptance testing.

## Precise count: 25 public upstream + 1 internal UI handler

Upstream `src/server.ts` constructs **25 normally advertised tools** in `tools/list`. Its `src/tools/schemas.ts` and dispatcher additionally recognize `track_ui_event` for internal MCP UI instrumentation, but `track_ui_event` is **not an entry in the public upstream `allTools` list**. Thus **26 recognized handler names but only 25 normally exposed upstream tools**, whereas Xoom v0.6 advertises all 26 in `tools/list`. Earlier project language saying "26 upstream public tools" was imprecise. This matters for host tool discovery.

**Parity ratings below:** **CORE** = useful equivalent core behavior but materially different scope or semantics; **NARROW** = only a small subset of the public upstream use cases; **INTERNAL** = implementation exists but differs intentionally from non-public upstream UI instrumentation. **FULL** requires argument, output, error, side effect and core supported-format equivalence, none of which is established here. The 26/26 figure means name/endpoint coverage, not functional parity.

**Rating interpretation:** None is proven fully identical in combined behavior, schema, error output and side effects. Multiple **CORE** entries are entirely adequate for current RAM development; **NARROW** entries are a useful foundation, but should never be called "full upstream parity". Some divergences are deliberate security design, not bugs.

## Cross-cutting MCP contract incompatibilities

These are critical even where the basic action works:

1. **Tool advertisement and metadata.** Upstream `tools/list` returns **25** visible definitions with Zod-derived schemas, descriptive behavior, `annotations` (e.g. `readOnlyHint`, `destructiveHint`, `openWorldHint`) and sometimes MCP UI `_meta`. Xoom has **26** simple hand-authored definitions with no annotations/UI metadata; several schema fields are absent or are declared but unused. `track_ui_event` is additionally public on Xoom.
2. **MCP result type.** Upstream replies with readable status/errors, sometimes `structuredContent` and multipart image/file content blocks. Xoom serializes most successful results into **a JSON string inside one `content[0].text` block**, and no images or preview `structuredContent`. A ChatGPT client or native Desktop Commander UI relying on upstream result shape will see different behavior.
3. **Error fidelity.** Upstream intentionally supplies granular `[NOT_FOUND]`, `[DENIED]`, diffs, timeouts, prompt/status descriptions and permission reports. Xoom mostly returns a JSON `{error:"..."}` marked `isError`; multi-file reads sometimes intentionally coarsen failures to `READ_DENIED_OR_FAILED`.
4. **File scope and binary support.** Xoom scratch: private UID/GID2000 mode0700 dirs/mode0600 files, max four path parts, 32KiB text and basic PDF output. Upstream configurable allowed directory set; empty list means whole filesystem; supports large files, richer formats, links and OS path conventions. This is a major *capability difference* and often a reasonable *recovery safety difference*.
5. **Configuration not actually applied.** Changing Xoom `fileReadLineLimit`/`fileWriteLineLimit` updates returned RAM preferences but does **not** currently govern read/write handling. Should correct semantics or remove/mark inert preferences before packaging.
6. **Existing-file write safety.** Upstream rejects an **omitted mode** when overwriting an existing nonempty file; Xoom defaults to rewriting. This is a concrete correctness/data-loss risk, independent of the need to support `append`.
7. **Process and search semantics.** Xoom `read_process_output.offset` is ignored; length means chars, not lines. Xoom search does not stream intermediate results; several supplied `start_search` fields are unsupported or limited. Tool-call compatibility is not achieved by accepting parameter names while ignoring them.
8. **Cloud transport and authorization.** Historical v0.3.1 full cloud tests and v0.4 read-only cloud search passed. v0.6's 26 tools were **physically locally tested only**; no v0.6 cloud acceptance. Prior write operations were blocked before Xoom dispatch despite the user's app-specific `Allow all actions` permission, so neither a host policy bypass nor an Xoom bug is established. The package must respect independent platform permissions.

## Safety review: keep intent, make it explicit

- The root controller currently permits only fixed read-only diagnostics and private root-owned immutable snapshot staging. UID2000 worker handles nested write/search/PDF operations; no broad root shell. That is an intentional advantage on an old recovery kernel. Do **not** turn an agent into unrestricted root simply to match upstream desktop semantics.
- Native Node `--permission` is defense-in-depth rather than a complete OS sandbox (old Linux 2.6.39, incomplete seccomp, possible AF_UNIX access to privileged services). Privilege escalation, absolute arbitrary filesystem access, arbitrary signal delivery and network access need separate threat review.
- Distinguish **formal API/shape parity**, **functional task parity**, and **privilege parity**. The goal should be *user-requested development capability with transparent security*, not equivalence of hazardous side effects.

## Recommended pre-package remediation roadmap

### Gate A — immediate correctness and interface semantics (P0)

- Fix `write_file` on existing nonempty file: explicit `rewrite` or `append` mode requirement, implement safe bounded append, and add atomicity/negative tests.
- Fix `read_process_output` documented offset/length to be **line-based with incremental cursor**, negative tail and timeout behavior, or narrow its schema to what is genuinely supported until implemented.
- Make configuration keys **effective** (or return explicit unsupported), implement actual read/write limits and validate all options strictly. Ensure no `tools/list` props silently imply capabilities absent in the runtime.
- Introduce a shared tool schema+return adapter for upstream-compatible `content`, `isError`, `structuredContent`, image blocks as needed, and `annotations`. Keep versioned Xoom-only restrictions visible rather than pretending full desktop capabilities.

### Gate B — high-value developer parity (P1)

- File handling: scalable multi-file text and nested directories, binary/image read as MCP image content, optional PDF/DOCX/Excel via explicitly managed safe converters. Longer source file support than 32KiB.
- Search: incremental bounded results, true cancellation, progress/outcome fields, gitignore/glob fidelity and time/size budgets. Recovery-compatible `rg` or equivalently reliable search, without imposing desktop-heavy dependencies blindly.
- Executions: meaningful **unprivileged development-shell** support under an explicit sandbox, with longer-running build/test processes, prompt detection and lifecycle/termination verification. Do not expand root capabilities or arbitrary PID kill access without a specific safety design.
- Add device-specific `xoom_display_info`, screen capture, watch and reversible TWRP preview operations **as extensions**, not part of standard upstream compatibility. Framebuffer `fb0` currently EBUSY, `fb1` sample readable but not proved to be active recovery screen.

### Gate C — production polish, optional upstream features (P2/P3)

- More complete PDF format/edit capabilities if genuinely needed on-device; otherwise expose clearly constrained PDF creator and use connected development hosts for heavier document processing.
- Persistent yet user-controlled stats/history and credential/config storage, redaction and opt-in telemetry; UI event parity only if an actual UI preview consumer exists.
- Recovery Toolkit packaging: user-controlled install/uninstall/rollback; dependency manifests, private loader, first-party browser auth, USB-backed config/credential policy; service lifecycle and DNS cleanup. Full remote acceptance and safe shutdown are separate gates.

## Suggested exit criteria for starting packaging

1. A version-pinned, documented **25 standard public tools + optional internal UI event** inventory.
2. All P0 contracts implemented, with upstream comparison tests and no silently ignored critical options.
3. P1 abilities sufficient for actual development workflows, or clearly declared unsupported by design; no unsafe privilege expansion.
4. Independent hardware tests, negative boundary tests, intentional rollback, v0.6 cloud regression/permission review.
5. The remaining UI framebuffer preview work may remain an opt-in extension, but its installation and security impact must be isolated from the Desktop Commander core.

**Conclusion:** We have completed an impressive **name coverage** milestone on real Tegra2 hardware, but not functional parity. The most cost-effective improvements are file I/O semantics, process I/O, schema/result shapes and safe developer workflow execution. Full upstream feature parity across Office, rich PDF, system-wide process control and arbitrary shell access is not a good blind prerequisite for a *prototype* recovery package; every divergence should instead be accurately disclosed and assessed against user needs.
