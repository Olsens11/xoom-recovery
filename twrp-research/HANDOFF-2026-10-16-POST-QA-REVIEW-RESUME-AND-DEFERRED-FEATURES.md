## 4. Time Sync — final authoritative design, CLOSED, not implemented

Source hierarchy: [final handoff](R22D4Q-TIME-SYNC-FINAL-DESIGN-HANDOFF-2026-10-15.md) + [authoritative decision register](R22D4Q-TIME-SYNC-AUTHORITATIVE-DECISION-REGISTER-2026-10-15.md) supersede older evolving proposals in the QA index and early research. **Proposed new revision R22d4q has not been built or flashed.** Existing Time Sync **0.2.1 Autoload ON, Autorun OFF** on last verified R22d4p (the future design makes both permanently enabled).

**Agreed:**
1. Time Sync is the **sole authority for actual recovery clock meaning**. Linux/TWRP's existing kernel clock still advances normally; no second artificial clock engine.
2. At every **Linux boot**, set wall clock *once*, as early as feasible and **before other packages consume time**, to `1970-01-01 00:00:00 UTC + elapsed time since this Linux boot`. This is normal default **UNSYNCED uptime presentation**, *even if inherited RTC/TWRP date seems plausible*. If initializer executes after 30s, display 00:00:30, not a new zero. UTC+0 24-hour display; never store past system times on SD. Don't infer time validity from the year.
3. Time Sync initializes **first**, Wi-Fi Runtime starts **second**. The usual trusted Toolkit boot worker is used (no separate second launch hook); minimal early boot helper is permitted if essential for the policy. No blocking recovery startup.
4. On each *real new connection* when LAN transitions to genuine `WIFI_READY`, launch a **bounded, asynchronous NTP attempt**, not endless polling. Avoid duplicate READY triggers. An existing prior NTP success this boot is not undone by subsequent disconnect or failed refresh.
5. Verified NTP success → actual calendar UTC kernel clock + current-boot state **SYNCED**, apply explicitly saved time zone/DST/offset and time format to native TWRP GUI. If no explicit preference, show UTC rather than adopt unverified defaults. Failed NTP before any success → uptime UNSYNCED persists. Manual Time Sync Run enables retry. Other packages read a simple public status, provisionally `xoom.time.synced`, 0/1, with distinct init ERROR if fallback fails.
6. SD is authoritative **for user time preferences only**; explicit frontend edits save settings and should never falsely report success if card absent. Rejected: prior-date SD checkpoints, arbitrary inherited RTC, multi-level confidence engine, SET TIME/SYNC TIME package action gating, periodic NTP polling, retroactive correcting previous report timestamps, blocking offline tools.
7. Header displays **literal UP alone** next to clock when UNSYNCED boot-relative uptime; **plain clock icon alone** when SYNCED, no check icon and no hourglass/stopwatch. Add concise context in Time Sync Help and native Settings only while integration active. Layout/ABI/timezone/time-setting interception still engineering tasks, not fresh product discussion.
8. Deliberately unresolved separate future: SD-card removal/reinsertion/absence behavior in overall Toolkit. Do not claim it settled by Time Sync decisions.

**Critical precedence trap:** old QA overview text says *Wi-Fi first, Time Sync second* or suggests SD time restoration, multiple SET TIME modes, retro-correction; **those texts are superseded by the final decision register**. Do not reintroduce old concepts.

## 5. Network Identity / Hostname — CORE DESIGN AGREED, FUTURE FEATURE PARKED

[Authoritative final design](NETWORK-IDENTITY-FINAL-DESIGN-HANDOFF-2026-10-15.md). NOT a separate ZIP; to live in Wi-Fi Runtime + existing Network settings page when its feature phase eventually starts. **Do not derail current six-package QA reviews or implement now.**

- Generated default: `xoom-recovery-` + six lowercase hex chars from **all 16 serial nibbles** of `ro.serialno` via tiny **nonstandard FNV-1a-style nibble-mixing** loop (initial 2166136261; XOR each nibble numeric value; multiply 16777619, mask 32 bits; low 24 bits printed as six hex). Example on tested Xoom: `xoom-recovery-87d89c`. Hash is noncrypto and collision possible; serial lookup `0.62–0.63s, arithmetic `0.01s.
- Actual **kernel hostname** is authoritative. At startup apply saved user custom name if present; otherwise generated default **without saving it**. An explicit **Set & Save** stores ANY valid value including text **identical** to generated default. **Restore Default** is an explicit action that clears the custom preference and applies generated name. This is about action provenance, not comparing strings.
- Existing Network settings UI: one editable hostname field and one context-sensitive button: nonempty valid → **Set & Save**; empty field → **Restore Default**. Clearing field without action changes nothing. Hostname syntax 1–63 ASCII alnum/hyphen, interior hyphens only, lowercased; no periods/spaces/underscores.
- Explicit offline Set & Save is allowed only after upfront warning that network uniqueness cannot currently be verified; persist pending-check marker. On later Wi-Fi ready, nonblocking collision check. Only an **actual confirmed collision with saved custom name** triggers automatic restore generated default + clears custom preference and leaves user-visible reason/history; ambiguous/silent/no-response is NOT proof. Default itself collision is an exception still to engineer.
- Out-of-band deliberate valid kernel hostname change (ADB/shell etc.) should also persist as custom value, even identical to default; startup initialization or re-applying internal value is not a deliberate user change. Efficient external-change detection is engineering work, and no-op same-value assignments may be fundamentally unobservable.
- Name update should propagate to mDNS later, but do not unnecessarily restart Wi-Fi/services; router DHCP/DNS caches aren't guaranteed to change instantly. SD durability/error and actual conflict mechanism need hardware proof.
- No changes installed.
