# R22d4q — Time-dependent package readiness, boot ordering, and SET TIME status (proposal)

**Status: DISCUSSION PROPOSAL / NOT YET USER-APPROVED FOR IMPLEMENTATION.** Recorded 2026-10-15 in the Round 2 clock-design discussion. **No code/build/flash/settings changes.** Installed recovery stays R22d4p.

## Explicit user decisions
- Preserve stock TWRP/Linux timekeeping. Core clock manager only tracks `UNSET` (1970/default), `ESTIMATED` (SD-restored or manually set, source recorded) and `SYNCED` (current-boot Time Sync confirmation). Manual setting must be available offline; restoring a last-known SD checkpoint does not prove the current time.
- **Retroactive correction of event timestamps is a FUTURE UPDATE, not part of R22d4q**, even though same-boot monotonic relative time could make it possible. Preserve notes in [the separate clock proposal](R22D4Q-CLOCK-TIME-CONFIDENCE-AND-SAME-BOOT-RETROCORRECTION-DECISION-2026-10-15.md); do not build it now.
- User favors the simpler Toolkit **SET TIME** status in a package row that prevents launching operations until the time requirement is satisfied. User is considering boot order Wi-Fi first, Time Sync second, then other packages, with a final successful-sync check to avoid races. We recommend an explicit completion handshake, not a timed post-sync delay.

## Proposed two-layer model: loader state vs time/readiness state
- Underlying verified package loader state remains `UNLOADED|LOADING|LOADED|FAILED` (plus standard service RUNNING/STOPPED), independent of wall-clock. Package manifest is pinned/verified and extracted normally unless a rare package's *load-time code itself* actually needs a time constraint.
- Toolkit **State column** displays prioritized user-action readiness derived from both layers: `UNLOADED` or `LOADING xx%`; `WAITING FOR TIME` while an already-started boot sync is unfinished; `SET TIME` when loaded but an action needs acceptable manual/network time; `SYNC TIME` when only successful recent network time qualifies; otherwise `LOADED`/`RUNNING`/`STOPPED`. Detail page still shows actual install state and reason. Don't set the package's underlying loader status to a fake `SET TIME` value.
- Row `SET TIME` and `SYNC TIME` are prompts/blocked-action indicators, not extra TWRP synchronization engines. Pressing a blocked Run/Start offers manual date+time or one-shot Time Sync when the package's requirement permits. The Time Sync package itself and Wi-Fi startup **never** have a time prerequisite, avoiding a deadlock.
- Existing legacy modules default to no hard requirement; e.g. Partition Inspector inspection, Log Collector and Network Diagnostics may still run/export offline and label timestamps `UNSET`/estimated rather than fabricating 1970 dates. Only a package action with an evidenced need for correct time receives a hard gate. `Stop`, `Unload`, manual date/time entry, package verification, backup/restore and emergency recovery operation are never blocked by time-confidence checks.
- For a package with multiple actions and mixed requirements, the summary State column shows the readiness of its **primary Start/Run action**, while details show precise requirements for each action (Run, Export, etc.). That retains the single-column simplicity and avoids overblocking unrelated actions. Recheck the requirement in the backend handler when pressed; display-only disable can be bypassed through ADB/scripts.
- A manual time entry and an older SD-derived estimate share the visible `ESTIMATED` category but retain **source metadata**, so a manifest requiring user-entered time (manual or synced) need not trust a potentially weeks-old SD checkpoint. A particularly strict action may require `SYNCED`; unauthenticated NTP should not be sold as cryptographically trusted time.

## Proposed boot-phase and dependency policy (not yet verified against native worker)
1. TWRP UI/recovery boot remains immediately available. After SD mount, establish clock provenance/last-known time if usable. A missing SD does not block recovery.
2. **Wi-Fi Runtime is the first optional module attempted by the boot worker when its saved Autoload flag is enabled.** The Wi-Fi service has *no time requirement*. If user intentionally disabled it, or saved profile/card unavailable, do not secretly override settings; Time Sync will have to remain waiting/unavailable, and other modules continue to load.
3. **Time Sync is next in dependency priority** when its saved Autoload flag is enabled. Loading verified Time Sync files needs no network or synchronized time. If its saved Autorun flag is enabled, run it **after an explicit `WIFI_READY` event**, not a fixed timer. Wi-Fi startup and NTP retries must have **bounded timeouts**. If not enabled, do not silently turn its existing OFF flag ON; surface an easy preference to opt in or prompt as needed.
4. Other package ZIPs can verify/load while Wi-Fi is connecting or NTP is running to avoid a new offline boot delay. **But no time-dependent Autorun may execute until its required time confidence is established.** The boot worker may serialize module loads if current architecture requires it, but must not mistake `SYNC_IN_PROGRESS` for completed failure. Noncritical modules may load/run while waiting; recovery UI always accessible.
5. Publish a **single authoritative, atomic, RAM-only completion record** for the clock coordinator on successful sync, containing boot-session token/generation, terminal result `SYNCED`, validated updated kernel UTC, and source; only publish it **after** NTP exits and time-setting + validation complete. Failure uses a terminal `FAILED/TIMED_OUT/WIFI_UNAVAILABLE` result and retains previous UNSET/ESTIMATED. Temporary `SYNCING` is an operation state, **not a fourth clock-confidence category**.
6. Any time-gated module's readiness is evaluated at/after its load, and reevaluated whenever the coordinator's completed-sync/manual-set state changes. The boot worker uses an explicit bounded join/result on the Time Sync job for gated Autorun. **Never sleep an arbitrary 250ms/1s/5s "to let sync propagate".** Readiness is based on a validated committed result, not on guessing when a UI refresh will reflect a state change.
7. After a successful sync, any waiting package row automatically changes from `WAITING FOR TIME` or `SET TIME` to its appropriate `LOADED`/`RUNNING` status. A user-initiated blocked action is **not launched automatically** without a fresh user press. If a package already had saved, explicitly authorized Autorun enabled, coordinator may release its pending Autorun **once** after the required confidence is met, subject to existing safety controls; no insecure wireless ADB POC exception/auto-exposure. If sync fails, leave it blocked and show why, not a global boot failure.

## Concrete examples
**Online fast:** Wi-Fi Autoload+Autorun ON, Time Sync Autoload+Autorun ON (only if configured). NTP starts at WIFI_READY. Strict package verifies/loads; row `WAITING FOR TIME`, then `LOADED` after verified SYNCED result. Its authorized AutoStart runs only after gate opens.

**Online slow:** NTP still running when a dependent ZIP is loaded -> row `WAITING FOR TIME`, no premature `SET TIME`. Sync finishes late -> immediate reevaluation triggered by coordinator (UI refresh may display it within normal 250 ms; no hardcoded post-sync sleep).

**Offline without valid clock:** Wi-Fi unready/disabled or NTP fails -> Time Sync reports why, clock stays UNSET or ESTIMATED. No global startup delay beyond bounded attempts. Strict package can still be loaded and configured; its primary Start shows `SET TIME` (manual acceptable) or `SYNC TIME` (network-only). Other safe operations work.

**Manual time:** User enters and confirms date/time via core recovery Settings, timezone clear; coordinator marks ESTIMATED with `source=manual`, reevaluates rows and unlocks manual-acceptable actions, not network-only ones.

**Untrusted SD snapshot:** Coordinator may conservatively set a lower-bound estimate, but strict `requires_user_set_or_network` actions remain blocked until explicit manual or NTP; do not confuse merely advancing 1970 to last saved date with precise current time.

## Suggested validation matrix before any flash
- Fast and delayed NTP, completion event immediately before/after module load, loading package while SYNCING, current-boot and stale RAM markers, double completion / only-once Autorun.
- Slow/failed/no Wi-Fi, disabled Time Sync Autoload or Autorun, missing/corrupt SD, cold 1970 default, stale timestamp checkpoint, manual-set and timezone handling, deep reboot state reset.
- Time-dependent Run via GUI and direct backend, Stop/Unload always available, no unintended insecure ADB startup, legacy reports export while time UNSET, footer and compact status-column label clipping.
- Verify R22d4p worker architecture and timing first. Development machines were offline during preceding review; user-facing sequence is design intent, not tested startup behavior. Update [canonical touch-index](TOOLKIT-TOUCH-COORDINATE-INDEX.md) for moved/new controls and preserve human-paced remote touch QA.
- Do not modify active R22d4p, existing saved Autoload/Autorun flags, pinned packages or partitions without agreed scoped change control / flash approval.

## Unsettled preference requiring explicit user approval
**Should Time Sync be an opt-in one-shot Autorun for existing users (the current Xoom has it OFF), or enabled by default on future fresh setups once Wi-Fi is configured?** Recommended: strongly recommend/offer ON for fresh setups, but never flip an existing user's saved OFF flag without their approval.
