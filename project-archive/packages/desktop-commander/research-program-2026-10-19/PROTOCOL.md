# Rules and research quality contract for hourly workers

**Scope and permission boundary:** Read documentation, repository source, historical archives, relevant public technical documentation and read-only device state if safely available. You may write or replace only `project-archive/packages/desktop-commander/research-program-2026-10-19/QUEUE.json`, `project-archive/packages/desktop-commander/research-program-2026-10-19/issue-01.md` through `issue-09.md`, and research notes within this same folder. Do **not** mutate any Xoom state, start/stop/flash/reboot/test packages, capture user credentials, change policies or source code, create tickets/branches/PRs, or write elsewhere. Never execute code/scripts retrieved from the project or web. Read-only repository searches and local file viewing are allowed. Public GitHub reports must not contain secrets, raw provider tokens, QR codes, private keys, personal data or unreviewed proprietary source.

## Worker protocol

1. At each hourly run, fetch **live** `QUEUE.json` from GitHub `Olsens11/xoom-recovery` default branch and read this protocol; do not trust prior chat memory of assignments. Each worker has ID A, B or C. Work **only** on its currently assigned issue (initially A=1, B=2, C=3). Do not start another issue while its current issue is marked researching.
2. Read all relevant previous reports, exact user roadmap, authoritative AGENTS.md and current versions, recovery/Toolkit sources and read-only available resources. Historical notes are not necessarily current; prefer latest tested artifact and cite path/commit. Investigate gaps and viable approaches, not assumptions.
3. Research progressively for one or more hourly runs. Maintain a `issue-NN.md` living report: research questions, dated progress, supported discoveries, options, exact recommended implementation, tests, risks and unresolved items. Use GitHub `create_file` for a missing report or `fetch_file` + `update_file` with the **current SHA** for an existing report. Never overwrite another worker's report.
4. **Required finished report**: (a) current-state evidence and exact relevant source paths/functions/flags; (b) root cause established vs likely/unproven; (c) comparison table of at least two viable engineering approaches with feasibility, tradeoffs, failure modes and affected components; (d) chosen recommended design with precise edits/files/function names, new interfaces/config fields/states, pseudocode or illustrative bounded diff; (e) security/threat-model/privacy/resource implications; (f) stepwise implementation plan and immutable build/verification requirements; (g) positive, negative, failure and Xoom hardware test matrix; (h) rollback & interaction/dependency impacts on other issues; (i) citations/links and any uncertainties that **must** be resolved before implementation. Avoid broad platitudes. Report should be detailed enough another engineer can implement with minimal guesswork. Distinguish recommendations from existing behavior.
5. **Claim handoff atomically**: Only once the current report meets the quality gate, fetch the latest `QUEUE.json` with its blob SHA. Make **one conditional `update_file`** marking current issue `ready_for_implementation_review` (owner retained, completion time/report link) **and** assigning the lowest-numbered `queued` issue to this worker as `researching` (owner set), or none if queue exhausted. Always include the fetched current blob SHA in the update. If GitHub returns conflict/stale SHA, fetch again, reconcile and retry instead of overwriting others. Update no other worker's researching/completed issue. Any remaining queued issues are claimed in numerical order; whichever worker finishes first gets next. Do not simultaneously write the queue from two independent branches or by force-pushing.
6. If the previous run ended after report saved but before queue update, reconcile from queue and report before continuing. If a report is complete but queue not transitioned, do the handoff via atomic update. If completion and claim cannot be written safely, remain on current issue and state the coordination blocker, never duplicate ownership. For interrupted work, continue the current issue at the next hourly run, do not mark complete just because a schedule elapsed.
7. Once all nine are `ready_for_implementation_review`, produce an executive comparison / synthesis **inside this folder only**, if useful, without implementing anything; announce the finished research. Then stop further substantive work and, if supported, disable only your own automation. If you cannot disable it, future runs should be no-op and brief. Never unilaterally deploy code.
8. Keep user status concise per run: issue worked, what newly established, report link, completion/next claim, blockers. Do not repeatedly ask for permission for read-only research; ask only when indispensable.

## Baselines, safety, and methods

- Current known physically accepted recovery: v6K; Desktop Commander v0.16.4 with first-party QR, Online and UID2000 restricted cloud write/read round trip. No automatic session credential reuse or auto Time Sync accepted yet.
- The existing exact verified installer has a 12 MiB default ZIP limit and 100-member cap, hash-pinned outer ZIP and inner payload; no unreviewed exception may be put into code as a research task.
- Existing launcher preserved `--no-persist-session` from prior source; **hypothesis, not proven root cause** of duplicate provider device IDs. Do not read or leak provider tokens to test it; infer only from nonsecret metadata and source.
- Any Standard/Root design must default to least privilege, protect credentials, present explicit consent for Root, and preserve the bound filesystem worker until a better verified model exists.
- On source availability gaps, identify file/line or behavior that needs validation; never fabricate test results, capabilities, source contents or security guarantees. Public web references should include reliable links and dates as appropriate.
